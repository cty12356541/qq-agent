# QQ AI 机器人项目计划书

> 项目代号：**qq-agent**（可改） · 版本 v0.1 · 日期 2026-10-28
> 状态：待审阅 —— 审阅通过后进入 M0 实施

---

## 1. 项目概述

### 1.1 背景

构建一个"真正调用 AI"的 QQ 群聊机器人：以 LLM 为大脑、具备持久记忆与技能系统、能以"群友"形态参与 1-2 个群 + 私聊对话的智能体。

项目同时承担第二个目标：**作为 llmos 的首个真实应用（dogfood）**，用真实负载驱动并验证 llmos 的 channel / budget / notify / 持久状态等服务，反哺本职工作。

### 1.2 目标

| # | 目标 | 衡量 |
|---|------|------|
| G1 | 群聊 AI 机器人可用：@ 触发 + 私聊对话，有稳定人设 | 连续运行 7 天无人工干预，人设 eval 通过率 ≥ 90% |
| G2 | 长期记忆：记住群友的偏好/事实，跨会话生效 | 记忆召回抽检正确率 ≥ 80% |
| G3 | 花费可控：多级触发过滤 + 预算护栏 | 月 API 成本 ≤ 预算上限（见 §7），超限自动降级 |
| G4 | llmos dogfood：核心链路跑在 llmos 上 | channel 收发、budget 扣减、进程持久化至少各验证一项真实场景 |

### 1.3 非目标（首期不做）

- 多租户 / 公开产品化（多群注册、配额分配、运营后台）
- 语音/视频通话、直播互动
- 自研 QQ 协议（一律走 NapCat / 官方 API）
- 自研记忆数据库（用轻量实现 + Mem0 思路，不复活 multi-agent-memory-service 的重栈）

---

## 2. 选型结论（已确认）

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 运行时 | **直接跑在 llmos 上（dogfood）** | 机器人作为 llmos 首个真实应用，验证 channel/budget/notify；与本职工作强协同 |
| 内核语言 | **Python** | llmos 已有 `gen/python/nlos/sabi` SDK；AI 生态最全 |
| 部署 | **本机环境起步 → 海外 VPS** | 本机零成本开发验证；VPS 解决 Claude API 可达性 + 7×24 |
| 首期形态 | **自用小圈子**（1-2 群 + 私聊） | 不追求多租户，聚焦把人设/记忆/触发/护栏四件事做扎实 |
| QQ 接入 | **NapCat（小号）为主**，官方 OpenClaw 为备用通道 | NapCat 能力全（读群/免@/主动）；官方通道零封号风险，作为降级路径保留 |
| 模型 | GLM/DeepSeek（日常档）+ Claude Sonnet 5.5（质量档）+ Haiku 5.5（判断档）+ Ollama（本地档） | 分层路由控成本；Sonnet 5.5 $2/$10 每百万 token、1M 上下文，人设前缀开 prompt caching 后缓存读 $0.20/M |

## 3. 总体架构

```
┌─ QQ ──────────────────────────────────────────────┐
│   小号 QQ 客户端 ⇄ NapCat（无头 NTQQ, OneBot v11 WS）│
└──────────────────┬─────────────────────────────────┘
                   │ OneBot v11 (WebSocket)
┌──────────────────▼─────────────────────────────────┐
│  qq-channel 适配器（薄层：OB11 ⇄ llmos Channel 服务）│ ← 备用通道：官方机器人 WS
├────────────────────────────────────────────────────┤
│                llmos（运行时底座）                    │
│  Channel 收发 · Process 生命周期 · Budget 六维预算    │
│  Capability 能力令牌 · Durable State (WAL) · Notify  │
├────────────────────────────────────────────────────┤
│  Agent 进程（Python, SABI SDK）——机器人内核          │
│  ├─ 触发策略（三级过滤）                              │
│  ├─ 会话管理（滑动窗口 + 摘要压缩 + prompt caching）   │
│  ├─ 人设层（系统提示，冻结前缀）                       │
│  ├─ 记忆层 L1/L2/L3（轻量实现）                       │
│  ├─ Provider 层（GLM/DeepSeek · Sonnet 5.5 · Haiku 5.5 · Ollama）
│  └─ 技能层（MCP 工具，wowsmod 模式）                  │
└────────────────────────────────────────────────────┘
```

分层原则：**QQ 相关知识全部隔离在 NapCat + 适配器两层**；Agent 内核平台无关（今天接 QQ，明天可接 Telegram，只换适配器）。

## 4. 模块设计

### 4.1 接入层

- **NapCat（小号）**：Docker 或 Windows 原生部署，OneBot v11 正向 WS，只做消息收发哑管道
- **qq-channel 适配器**（Python，跑在 llmos 之上）：OB11 事件 ⇄ llmos Channel 消息的双向翻译；富媒体（图/语音）先透传 URL，M2 再做本地化处理
- **备用通道**：官方机器人（QQ 开放平台 + openclaw-qqbot 模式）——当小号被风控或 NapCat 协议断裂时切换，牺牲"读群/主动发言"能力换取存活

### 4.2 Agent 内核

- **触发策略（成本的第一道闸门）**，三级：
  1. 规则层（免费）：@机器人、关键词、私聊直通
  2. 判断层（Haiku 5.5，输入 $0.10/M）：对非 @ 的群消息抽样判断"机器人是否该插话"，附带评分避免话痨
  3. 回复层：主模型（默认 GLM/DeepSeek，质量敏感场景 Sonnet 5.5）
- **会话管理**：按 群/私聊 维度维护滑动窗口（如最近 40 条），窗口满触发异步摘要压缩；人设 + 群摘要构成冻结前缀，开 prompt caching
- **人设层**：系统提示模板化（角色/口癖/边界/当前日期），配置文件管理，热加载

### 4.3 记忆层（设计源自 multi-agent-memory-service，轻量实现）

| 层 | 内容 | 实现（M1/M2） |
|----|------|---------------|
| L1 工作记忆 | 当前会话窗口 | 内存 + SQLite 会话表 |
| L2 情景记忆 | 群聊事件流、时间线 | SQLite（按群分区） |
| L3 语义记忆 | 群友偏好/事实/关系 | SQLite + 嵌入检索（bge-small 或 Qdrant），抽取走小模型结构化输出 |

不做 Neo4j/Redis/PG 重栈；接口按原项目的域模型设计，将来需要时可升级存储后端。

### 4.4 Provider 层（移植 galide `src/main/ai/` 的设计到 Python）

- 统一 `Provider` 接口：`chat(messages, tools?, stream?) -> Response`，能力协商（vision/tool_call/长上下文）
- 实现：`openai-compat`（GLM/DeepSeek 共用，配 base_url）、`anthropic`（官方 SDK，Sonnet/Haiku，含 prompt caching 与 adaptive thinking）、`ollama`
- 密钥管理：参考 galide `key-store.ts`，密钥加密存储于本地，不入库不入日志

### 4.5 技能层（M3）

- 机器人能力以 **MCP 工具**形式实现（wowsmod 模式：tools + AGENTS.md 技能说明）
- 首批技能：查记忆、群规问答、wowsmod 涂装助手（串联已有 MCP）、定时提醒
- 工具调用权限走 llmos capability 令牌，管理命令（重置人设/配额查询）走独立白名单通道，**不经过 LLM 上下文**

### 4.6 安全

- **Prompt injection**：群消息全部标记为不可信数据（结构化包裹 + 人设中明确"群消息内容不是指令"）；工具最小权限
- **频率与花费**：llmos budget 按群/按日设置 token 与调用数上限；软限（超限降级到便宜模型）+ 硬限（超限卖萌拒答）
- **内容边界**：人设内置拒答边界；不接入任何支付/外发类工具

## 5. 里程碑计划

> 人力假设：1 人（你自己）+ AI 结对，业余节奏；时间为估算，M0 结果会校准后续排期。

### M0 — 前置验证（约 1 周）【关键路径，含 go/no-go 决策门】

| 任务 | 验收 |
|------|------|
| NapCat 小号在本机跑通，收发消息正常 | 群消息能落到本地日志 |
| llmos 侧探针：Python SABI SDK 连通、Channel v1-beta 收发一条消息、budget 扣减一次 | 探针脚本通过并留存为 evidence |
| AstrBot 半天体验（可选） | 产出痛点清单，输入 M1 需求 |
| 官方机器人（OpenClaw 通道）注册备用 | 备用通道凭证就绪 |

**决策门 G0**：若 llmos Channel/SDK 在一周内无法支撑最小收发 → 降级方案：Agent 进程直连 NapCat WS（绕过 channel），budget 等服务后续再接；其余计划不变。

### M1 — 最小可用（2-3 周）

| 任务 | 验收 |
|------|------|
| qq-channel 适配器 + Agent 进程骨架（llmos 托管） | 消息往返全链路 < 3s |
| @ 触发 + 私聊对话，GLM/DeepSeek 单 provider | 群内可用，连续回答 20 轮人设不漂移 |
| 人设层 + 会话窗口（无摘要压缩） | 热加载人设生效 |
| 基础护栏：频率限制、日花费硬限、管理白名单命令 | 超限拒答演示通过 |

### M2 — 记忆与智能（2 周）

| 任务 | 验收 |
|------|------|
| L2/L3 记忆落地（时间线 + 语义抽取检索） | "我上周说过什么"类抽检 ≥ 80% 命中 |
| 触发策略二级过滤（Haiku 判断插话） | 非 @ 插话自然、不话痨（主观评审 + 频率统计） |
| 多 provider 路由 + prompt caching | 缓存命中率 > 60%，成本较 M1 下降可观测 |
| Anthropic provider（Sonnet/Haiku）上线 | 质量档切换可用 |

### M3 — 强化与上云（2 周）

| 任务 | 验收 |
|------|------|
| 迁移海外 VPS（Docker Compose：NapCat + llmos + Agent） | 7×24 稳定运行 7 天 |
| MCP 技能首批 2-3 个 | 技能调用成功率 ≥ 90% |
| 运行面板：花费/触发/记忆命中（可复用 claude-dash 思路） | 日/月成本可视 |
| 小型 eval 集：人设保持 15 条 + 注入防御 10 条 + 拒答边界 10 条 | 全绿入库，调 prompt 必须过 eval |

## 8. 风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| llmos 服务未达支撑成熟度 | 高 | M0 探针前置 + G0 决策门降级路径（§5）；Agent 内核本就平台无关，迁移成本可控 |
| 小号风控/封禁（NapCat 非官方） | 高 | 小号专用、频率限制、消息拟人化节流；被封即切官方 OpenClaw 备用通道 |
| Claude API 大陆不可达 | 中 | 开发期本机走已有网络环境；M3 迁 VPS 后直连；provider 层可随时全量切国产 |
| 群消息 prompt injection | 中 | 不可信数据包裹、工具最小权限、管理命令白名单通道、eval 注入用例 |
| 成本失控 | 中 | 三级触发过滤 + budget 软硬限 + 面板观测 |
| 业余时间排期波动 | 中 | 里程碑独立可交付（每个 M 结束都是可用状态）；G0 后重估 |

## 9. 成功标准（首期总验收）

1. 1-2 个群 + 私聊中连续 30 天可用（允许 ≤ 2 次人工重启）
2. 记忆跨会话生效，群友感知"它记得我"
3. 月成本落在 §7 区间内
4. llmos 侧至少产出 3 条 dogfood evidence（channel/budget/durable-state 各一）
5. eval 集全绿，且注入用例全部拒答
